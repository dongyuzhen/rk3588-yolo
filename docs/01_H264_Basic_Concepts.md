# 必知必会 01：H.264 视频流核心概念

为了让你彻底通透这个项目，我们将视频流中最核心的概念浓缩为以下几点。看完这篇，你就能看懂大部分流媒体的专业术语。

## 1. I帧 与 P帧 的真实依赖关系

你在总结时说“I帧需要P帧的动作加起来才是完整流”，**这个理解要反过来**：
*   **I 帧（关键帧）是“独立自主”的**。它自己就是一张完整的全景照片。没有任何前面的帧，它也能被完美解出来。
*   **P 帧（预测帧）才是“啃老族”**。它里面只存了“残影和位移”。如果要解出一个 P 帧，播放器必须先找到它前面的那个 I 帧，然后把这个 P 帧的位移加在 I 帧上，才能拼出一张新图。

**真实推流场景中的情况**：
如果推流时网络丢包，丢了一个 P 帧，画面只会卡顿或者花屏一下（因为后面的 P 帧算错位置了）；但如果**丢了一个 I 帧**，那接下来所有的 P 帧全都会废掉，画面会一直卡死，直到下一个 I 帧出现（这在术语里叫 GOP，通常设置为 2 秒一个 I 帧）。

## 2. SPS 和 PPS (序列参数集/图像参数集)

你的理解非常精准：它们就是**“解码说明书”**（Header 消息）。
*   **SPS (Sequence Parameter Set)**：管整个视频序列的宏观参数，比如视频的长宽分辨率。
*   **PPS (Picture Parameter Set)**：管图像内部解码的具体算法参数。

**工作原理**：
播放器连接上 RTSP 服务器后，收到的第一个包**必须**是 SPS+PPS，紧接着第二个包**必须**是 I 帧。
如果没有 SPS/PPS，播放器就算拿到了 I 帧，也不知道这个图片是 640x640 还是 1920x1080，直接拒绝解码。

## 3. PTS 和 DTS (时间同步)

*   **PTS (Presentation Time Stamp, 展示时间)**：决定画面什么时候上屏幕。
*   **DTS (Decoding Time Stamp, 解码时间)**：决定画面什么时候进解码芯片。
*   如果没有 B 帧（双向预测帧，通常为了降低延迟，实时推流会关掉 B 帧），那么 PTS 永远等于 DTS。
*   在我们的代码中，每推一帧，PTS 就需要加上 `1000/FPS`。告诉播放器，下一帧在 33.3 毫秒之后播放。

## 4. 总结：视频流的长相

一段标准网络 H.264 视频流（按时间顺序）长这样：
`[SPS] -> [PPS] -> [I帧] -> [P帧] -> [P帧] -> [P帧] ... (过两秒) ... -> [SPS] -> [PPS] -> [I帧] -> [P帧] ...`

只要我们的 MPP 能按这个顺序吐出数据，FFmpeg 就能把它完美推走。
