## 一、30 秒电梯演讲

> 面试官：简单介绍一下你这个项目。

我在 RK3588 上做了个智慧工地的实时安防检测系统。摄像头 1080P 60 帧拍工地画面，NPU 跑 YOLOv5s 检测有没有人不戴安全帽、不穿反光背心，检测结果画框叠加后 H.264 硬编码，RTSP 推流出去。检测到违规就拍照存证、飞书机器人告警。

核心亮点是**全链路零拷贝**——摄像头拍到的那帧数据，从 RGA 做预处理、到 NPU 做推理、再到 MPP 硬编码，整个过程数据都在 DMA-BUF 里面传，CPU 从来不拷贝。所以 1080P 60 帧的流，CPU 占用率只有 **5%** 左右，端到端延迟不到 200 毫秒。

## 二、项目全景（画给面试官看）

> 面试官：整体架构是什么样的？

一共有四条线程，两个队列，一条数据链路：

```
摄像头(V4L2)                          飞书告警
    │                                    ▲
    │ NV12 dmabuf fd                     │ webhook
    ▼                                    │
[采集线程] ──→ readQueue ──→ [推理线程池×3]     [报警引擎线程]
                              │   │              ▲
                              │   │ future       │ 违规事件
                              ▼   ▼              │
                           writeQueue ──→ [写出线程] ──→ MPP编码 → RTSP推流
```

**采集线程**：从 V4L2 摄像头拿 NV12 帧，丢进 readQueue。不拷贝，只传 dmabuf fd。

**推理线程池**：3 个 worker，每个绑一个 NPU 核心。从 readQueue 取帧，走 RGA 预处理 → NPU 推理 → 后处理，把结果连同原始帧 fd 一起丢进 writeQueue。

**写出线程**：从 writeQueue 取帧，CPU 在 BGRA 透明图层上画框，RGA 把 BGRA 叠加到 NV12 上送 MPP 编码，编码完 RTSP 推流。同时检查违规，有就推送给报警引擎。

**报警引擎线程**：独立运行。漏桶防抖（连续 15 帧才报警），每类违规 30 秒独立冷却，触发后拍照 + 飞书 Webhook。

## 三、为什么选 RK3588？

RK3588 这颗芯片有三个 NPU 核心（6 TOPS INT8），同时有 RGA 硬件图像加速器和 MPP 硬件视频编码器。关键在于这三种加速器都挂在同一个 IOMMU 下面，可以用 DMA-BUF 在不同硬件之间传数据。

对比：
- **Jetson Nano**：贵，GPU 推理延迟高
- **树莓派 + 加速棒**：USB 带宽瓶颈
- **海思**：NPU 强但 SDK 不开源
- **RK3588**：便宜（开发板几百块），SDK 开源，NPU/RGA/MPP 三件套齐全，DMA-BUF 零拷贝

## 四、零拷贝是怎么实现的？（重点）

> 面试官：你说零拷贝，具体怎么做到的？

零拷贝不是说完全没拷贝，而是 **CPU 不参与数据搬运**。数据全在 DMA-BUF 里，硬件之间通过 IOMMU 直接访问同一块物理内存。

**一帧数据的旅程：**

**① 摄像头拍到 NV12 帧**
V4L2 驱动用 `V4L2_MEMORY_MMAP` + `V4L2_BUF_FLAG_EXPORT`，摄像头 ISP 通过 DMA 把 NV12 写进内核分配的 buffer。用户态通过 `VIDIOC_EXPBUF` 导出为 dmabuf fd——这个 fd 只是个整数，不包含像素数据。

**② RGA 预处理**
调 `importbuffer_fd(camera_fd)` 把摄像头 fd 注册给 RGA 驱动。RGA 通过 IOMMU 直接 DMA 读摄像头帧，做完色彩转换+缩放，DMA 写入 NPU 输入 buffer（通过 `rknn_create_mem` 预分配，物理连续，带 fd）。

```
importbuffer_fd(camera_fd)       → RGA 能读到摄像头帧
improcess(NV12→RGB888 + 1920→640)
RKNN input buffer                ← RGA 硬件直接写
```

**③ NPU 推理**
初始化时用 `rknn_create_mem` 分配输入输出 buffer，`rknn_set_io_mem` 绑定到模型 I/O 张量。RGA 的输出就是 NPU 的输入——RGA 写完，NPU 直接读，CPU 不碰。

**④ OSD 叠加 + MPP 编码**
CPU 在一小块 BGRA 画布上画框（必须 CPU 做），然后 RGA 跑 `improcess` 一步完成「NV12 拷贝 + BGRA Alpha 叠加」→输出到 MPP 输入 buffer。MPP 通过 `mpp_buffer_import_with_tag` 导入 fd，硬件编码器通过 IOMMU 直接读——RGA 写完，MPP 就编码。

**实测数据（1493 帧平均）：**

| 阶段 | 耗时 | 说明 |
|------|------|------|
| RGA 预处理 | **2.1ms** | NV12→RGB640 letterbox |
| NPU 推理 | **25.5ms** | YOLOv5s INT8, 3核并行 |
| RGA OSD 叠加 | **3.5ms** → **2.0ms** | 优化前后 |
| MPP 编码 | **4.2ms** | H.264 1080P |
| CPU 占用 | **~5%** | 全链路 |

如果 CPU 做这些（OpenCV + 软编码），一帧至少 60-80ms，CPU 占 80%+。

## 五、三线程流水线架构

> 面试官：多线程怎么设计的？

三个阶段拆成三条线程，生产者-消费者模型：

```
采集 ──[readQueue:4]──→ 推理×3 ──[writeQueue:4]──→ 写出
```

**队列深度设计**：readQueue=4 + writeQueue=4 + inflight≤4 = 12 ≤ V4L2 buffer=12。永远至少 1 个 buffer 在驱动手里，不会 POLLERR。

**帧序保证**：推理线程池用 `std::map<int, InflightTask>` 按采集序号排序输出。后面提交的帧即使先算完，也被前面的 inflight 挡住，严格按序。

**实测吞吐**：WriteFrame 平均 16.64ms ≈ 60 FPS。其中约 8.8ms 是队列等待（线程空闲），实际工作约 7.8ms。NPU 3 核并行有效吞吐 115 FPS，远超需求。

## 六、IoU 目标追踪器

贪心 IoU 匹配 + 速度预测，纯 C++，无第三方依赖。

1. 新检测结果和活跃 Track 做 IoU 矩阵
2. 按 IoU 降序贪心配对（每对只能匹配一次）
3. 匹配上 → 更新位置（EMA 平滑），miss 清零
4. 没匹配上新框 → 新建 Track
5. 连续 8 帧没匹配 → 删除 Track
6. 命中 ≥2 帧才输出（过滤单帧误检）

速度预测：用上帧位移做线性外推，快速移动也不容易跟丢。整个 update 耗时 **0.01ms**。

**为什么不用 DeepSORT？** 需要额外的 ReID 网络，边缘跑不动。工地场景 IoU 够了。

**对报警系统的增益**：track_id 作为人员锚点，报警引擎按 "label + track_id" 做 ID 级去重冷却。

## 七、报警引擎设计

独立线程，和视频流水线完全解耦。

**漏桶防抖**：出现 +1，缺席 -2，积分 ≥ 15 才触发（约 0.5s）。容忍约 33% 漏检率，过滤单帧抖动。

**多类别独立冷却**：每类违规（如 "no-helmet#3"）各自维护 30 秒冷却期。同一个人 30 秒内不重复推送，但其他人独立触发。

**IO 隔离**：存图 + 飞书 Webhook curl 通过 `std::thread(...).detach()` 异步执行，不阻塞报警主循环。

## 八、看门狗故障恢复

工地上环境恶劣，摄像头可能松动、NPU 可能过热。

**摄像头恢复**：连续 30 帧失败 → stopStreaming → closeDevice → 等 2 秒 ISP 预热 → re-init → startStreaming。恢复后给 5 秒宽限期避免误触发。

**NPU 恢复**：连续 10 帧失败 → delete ThreadPoll → 等 300ms → new ThreadPoll 重新加载模型。

**协议**：流水线线程通过 `recovering` 原子变量自旋等待。最多重试 3 次，超限写 FATAL 日志。

## 九、踩过的坑（面试官最爱问）

### 坑 1：BGR/RGB 通道错位 → mAP 暴跌

**现象**：模型转换后 mAP 从 85% 掉到 60%+。

**原因**：训练用 RGB，OpenCV 默认 BGR，送进 NPU 前没转换。红色安全帽变蓝色，特征提取全崩。

**解决**：RGA 转换时明确指定 `RK_FORMAT_RGB_888`。修复后 mAP@50 = **84.2%**。

### 坑 2：CMA 内存耗尽

**现象**：V4L2 初始化报 `Cannot allocate memory`。

**原因**：RK3588 默认 CMA 只有 8MB，12 个 1080P NV12 buffer 每个 3MB，完全不够。

**解决**：V4L2 用 MMAP 让驱动自己管内存，工作 buffer 用 `/dev/dma_heap/system`（非 CMA，RGA 通过 IOMMU 访问），RKNN buffer 走内部 DMA heap。

### 坑 3：RGA 双次 DMA 浪费

**现象**：OSD 叠加 3.53ms，比预期高。

**原因**：`imcopy(src→dst)` + `imblend(osd→dst)` 两步，每次都是独立 DMA 传输，启动延迟叠加。

**解决**：合并为 `improcess(src, dst, osd)` 一步完成。同时把 mpp_fd/osd_fd 的 RGA handle 提前 import 缓存。优化后：**3.5ms → 2.0ms**。

### 坑 4：NMS 索引映射错误 → 幽灵框

**现象**：同一个目标出现多个重叠框。

**原因**：排序后用排序序号去取 classID，而不是用排序后映射回原始索引。

**解决**：NMS 循环统一通过 `indexArray` 做索引映射。

### 坑 5：Cache 一致性 → 画面撕裂

**现象**：RGA 合成后偶尔上半帧新、下半帧旧。

**原因**：CPU 画完 BGRA 后数据还在 L1/L2 cache，没刷到 DDR。RGA 读 DDR 拿到脏数据。

**解决**：`osd_cma.syncEndWrite()` 在 RGA 操作前强制 flush CPU cache。

## 十、性能测试方法

实现了**零开销计时框架**（`bench/perf_timer.h`），CMake 选项 `-DBENCH_MODE=ON` 控制。

**设计**：RAII 作用域计时器。`PERF_SCOPE("stage_name")` 放在代码块开头，退出自动记录。`BENCH_MODE=OFF` 时所有宏展开为空，编译器完全剔除。

**插桩点**：RGA_preprocess、NPU_inference、Post_process、Tracker_IoU、OSD_draw、RGA_blend、MPP_encode、WriteFrame_total。

**统计**：avg / min / max / p50 / p99 / p999。每 300 帧打印表格 + 写 CSV。

**RGA vs OpenCV 专项**：`./app --bench-rga`，采集一帧真实图像，用 RGA 和 OpenCV 各跑 100 次相同操作，输出加速比。

| 操作 | RGA | OpenCV | 加速比 |
|------|-----|--------|--------|
| NV12→RGB+640缩放 | **1.6ms** | 4.5ms | 2.8x |
| BGRA→NV12 Alpha叠加 | **3.5ms** | 44.5ms | **12.9x** |
| 简单 NV12→BGR | 1.4ms | **1.2ms** | 0.8x（NEON 略快）|

关键发现：简单色彩转换 OpenCV 略快（A76 NEON 很强），但复合操作 RGA 碾压。正确策略是复合操作用 RGA，简单的按需选。

**NPU 扩展性**：

| 配置 | 单帧延迟 | 吞吐 | 效率 |
|------|---------|------|------|
| 1核 | 25.3ms | 39 FPS | 基线 |
| 2核 | 25.5ms | 78 FPS | 98% |
| 3核 | 25.8ms | **115 FPS** | 97% |

近线性扩展，硬件隔离很好。

## 十二、面试高频追问

**Q：为什么不直接用 OpenCV DNN？**
ARM CPU 推理 YOLOv5s 约 200-300ms/帧，完全跟不上 60FPS。NPU 只需要 25ms。

**Q：三个 NPU 核不会打架吗？**
每个 YOLO 实例独立绑核（`rknn_set_core_mask`），1核→3核扩展效率 97-98%，几乎无竞争。

**Q：队列满了怎么办？**
`enqueue_drop_oldest`——宁可丢老帧也不阻塞采集线程，否则 V4L2 驱动 buffer 耗尽全链路崩溃。

**Q：延迟 200ms 怎么算的？**
采集 16ms + 推理 8ms + 编码 8ms + RTSP 传输 50-150ms ≈ 80-180ms，上限 200ms。

**Q：如果重新设计会改什么？**
1. 配置外置（YAML/JSON）
2. 报警 webhook 改异步 HTTP 库
3. Systemd 进程级兜底
4. 追踪器可换 ByteTrack（边缘也能跑）

**Q：用了哪些 C++17 特性？**
结构化绑定、`if constexpr`、`std::shared_ptr` 自定义 deleter、`inline static`、`std::call_once`。

## 十三、5 分钟精简版

1. **做什么**：RK3588 智慧工地安防，安全帽+反光背心检测，1080P 60FPS，CPU 5%，延迟 <200ms。

2. **核心亮点**：全链路零拷贝。V4L2→RGA→NPU→MPP，DMA-BUF 直通，CPU 不搬运像素。实测 RGA 预处理 2.1ms，NPU 推理 25.5ms（3 核 115FPS），MPP 编码 4.2ms。

3. **架构**：三线程流水线 + 有界队列。IoU 追踪器分配稳定 ID。独立报警引擎，漏桶防抖 + 类别独立冷却，飞书告警。

4. **踩坑**：BGR/RGB 错位 mAP 暴跌→修复 84.2%。CMA 耗尽→MMAP+system heap。RGA 双次 DMA→合并 improcess 省 1.5ms。NMS 索引错误→indexArray 重映射。

5. **测试**：RAII 计时框架 + 编译开关，1493 帧全阶段数据（p50/p99/p999 + CSV）。RGA vs OpenCV 专项：简单转换 0.8x 略慢，复合操作 12.9x 碾压。
