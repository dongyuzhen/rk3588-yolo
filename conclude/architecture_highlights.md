## 🌟 亮点一：基于背压机制的流媒体零延迟队列设计

### 1. 业务痛点 (Situation)
在边缘计算设备（RK3588）上部署流媒体 AI 识别流水线时，常常面临**生产与消费速率不匹配**的问题。
* **上游**：V4L2 摄像头稳定输出 30 FPS。
* **下游**：NPU 目标检测算力存在波动（可能降至 20-25 FPS），或者推流端因为网络抖动导致发送阻塞。
如果不做特殊处理，多余的帧会堆积在队列中。最终反映在拉流端，就是画面严重滞后（累积延迟可达数秒以上），这在安防实时告警场景下是致命的。

### 2. 架构决策与 Trade-off (Task & Action)

为了实现真正的“零延迟感知”，必须引入丢帧机制。但我没有采用暴力的“全局丢帧”，而是设计了基于双队列的**天然背压（Backpressure）机制**：

* **决策 1：下游队列（NPU -> 推流）绝对不丢帧**
  * *原因*：进入此队列的帧已经消耗了 NPU 极其昂贵的推理算力。如果在推流前丢弃，等于 NPU 做了无用功。
  * *策略*：使用条件变量阻塞等待。当网络拥堵推流变慢时，该队列会阻塞 NPU 推理线程。
* **决策 2：上游队列（摄像头 -> NPU）实行“丢弃最老帧（Drop-Oldest）”**
  * *原因*：这里的帧是刚刚采集的原始图像，还没有投入任何算力，丢弃成本为 0。当 NPU 被下游阻塞时，上游队列迅速填满，此时强行挤出队列头部最老的帧，永远把最新鲜的画面喂给 NPU。

### 3. 工程实现优雅度：C++11 泛型 Lambda 回调解耦
在处理丢弃老帧时，面临一个极其容易踩坑的资源泄露问题：**丢弃的旧帧中包含了 V4L2 的 `dmabuf` 描述符，如果不主动归还给驱动，4个缓冲池耗尽后整个相机将彻底死锁。**

为了保持底层数据结构 `SafeQueue` 的纯粹性，我重构了入队接口：
```cpp
// SafeQueue.h 内部：缩小锁粒度，回调在解锁后执行避免死锁
template <typename DropHandler>
void enqueue_drop_oldest(T val, DropHandler on_drop);

// main.cpp 调用方：通过 Lambda 表达式处理资源释放，彻底消灭外层空壳变量
g_readQueue.enqueue_drop_oldest(f, [](CapturedFrame& dropped) {
    g_camera.releaseFrame(dropped.packet);
});
```
这种设计将“队列满怎么弹”交到底层，把“弹出来的资源怎么释放”交还给业务层，逻辑内聚，极大地提升了并发安全性和代码可读性。

### 4. 最终收益 (Result)
* 解决了长连接运行下内存暴涨与画面严重延迟的顽疾，将端到端延迟死死控制在 2 帧以内（< 60ms）。
* 架构上具备极强的弹性，无论是 NPU 算力瓶颈还是网络带宽瓶颈，都能自动降级应对，保证系统的鲁棒性。

## 🌟 亮点二：基于 RGA 硬件加速的零拷贝 Letterbox 预处理

### 1. 业务痛点 (Situation)
在机器视觉中，直接拉伸（Resize）原始图像去匹配模型输入分辨率，会导致图像严重形变（如安全帽被压扁变形），大幅降低目标检测的精度。
标准的解法是 **Letterbox 缩放**（保持长宽比缩放，两边填充灰边）。但在边缘侧，如果使用 CPU（如 OpenCV）来做色彩转换（YUV->RGB）和 Letterbox 填充，会消耗大量 CPU 算力，导致整体帧率严重下跌。

### 2. 硬件加速与踩坑决策 (Task & Action)
我决定完全利用 RK3588 内部强大的 2D 硬件引擎（RGA）来一步完成预处理。但在实现时，遇到了严重的硬件对齐坑与性能抉择：

* **核心挑战：RGA3 的 RGB888 对齐限制**
  在做 Letterbox 灰边填充时，我最初调用了 `imfill`。但内核日志抛出 `RGA_COLORFILL fail: Invalid argument`。
  *深入分析*：RK3588 内部的 RGA3 核心为了追求极致的高带宽吞吐，在硬件电路上移除了对 3 字节非对齐格式（如 RGB888）的单色填充支持，只支持 RGBA8888 这样的 4字节对齐格式。
* **架构坑点与纠正：动态分辨率解耦与 4 字节严格对齐**
  底层推理模块（`Yolov5s`）如果硬编码摄像头分辨率（如 640x480），在更换高清摄像头（1080p）时将导致严重的缩放畸变。为此，我将相机尺寸作为参数通过线程池层层透传给底层 NPU 实例，实现了解耦。同时，为了防止 RGA 在处理目标内存偏移时出现 DMA 越界或花屏，我将 Letterbox 的 Padding 参数严格拉伸至 **4 字节对齐**（`(pad / 4) * 4`），完美迎合了硬件 Stride 的苛刻要求。
* **架构抉择：拒绝引入多余的 DMA 中转**
  一种妥协做法是：先创建一个 RGBA8888 的中间 DMA 缓冲区做硬件填充和处理，再转成 RGB888 喂给 NPU。
  *我的决策*：坚决反对！引入中间 Buffer 会导致额外的一次完整图像读写，直接让 DDR 内存带宽消耗翻倍，违背了端侧极致性能的“零拷贝”原则。

### 3. 极致性能解法：CPU 与 RGA 的异构协同
我巧妙地利用了**同一块物理 DMA 内存的两个视角**来解决这个死局：
1. **CPU 视角极速填充**：因为目标尺寸是固定的（如 640x640x3 = 1.2MB），我在初始化时通过 `rknn_create_mem` 申请了 DMA 内存。这块内存映射到了 CPU 的虚拟地址（`virt_addr`）。对于仅仅 1.2MB 的纯色填充，CPU 的连续 `memset` 甚至比发起一次完整的硬件 RGA 调度还要快！
2. **RGA 视角零拷贝渲染**：灰边铺好后，我将这同一块物理内存的 `fd` 包装成硬件句柄，调用 `improcess`。RGA 硬件直接从摄像头的 YUYV 源地址抠图、缩放并**精准覆盖**到目标内存的中心位置。

```cpp
// 1. CPU 视角：以极低开销完成 1.2MB RGB888 灰边填充（绕过 RGA3 硬件限制）
memset(input_mem_->virt_addr, 114, (size_t)model_width * model_height * 3);

// 2. 硬件视角：RGA 一步完成 YUYV->RGB888 色彩转换、缩放并精准摆放至中心
improcess(src_yuyv, dst_model, empty_pat, srect, drect, prect, IM_SYNC);
```

### 4. 最终收益 (Result)
* **绝对的零拷贝 (Zero-Copy)**：从摄像头抓取（V4L2）到 NPU 推理，中间完全没有发生任何 DDR 之间的数据搬运拷贝，榨干了硬件性能。
* **无损精度**：完美实现了硬件级的 Letterbox 预处理，消除了目标形变漏检，为后续 1080p / 4K 高清 MIPI 摄像头的接入预留了充沛的总线带宽。
