## 1. 推理过程 NPU 利用率是多少？

项目运行时通过 `cat /sys/kernel/debug/rknpu/load` 查询 NPU 三核利用率。

实测在**双线程（2个 NPU 核心并行）** 时，NPU 利用率约为 **60%~80%**。整体流水线瓶颈不在 NPU，而在写出线程（RGA+OpenCV+MPP+RTMP串行），NPU 推理实际有空闲等待窗口。

设计上使用了 `rknn_set_core_mask` 将三个 Yolov5s 实例分别绑定到 `RKNN_NPU_CORE_0 / 1 / 2`（`yolov5s.cpp:70-74`），理论上三核同时满负荷。但由于 CMA 内存压力（RK3588 CmaTotal 仅 8MB），最终将线程数从 3 降至 2，只用了两个 NPU 核（Core 0 和 Core 1）。

## 2. RGA 做 BGR→NV12，为什么不用 OpenCV 或者 CPU 做？3.4ms 是怎么测出来的？

### 为什么用 RGA 不用 OpenCV/CPU？

有三个核心原因：

**① 硬件零拷贝，完全不占 CPU**

RGA（Rockchip Graphics Accelerator）是 RK3588 内置的 2D 图像硬件加速 IP，格式转换由专用硬件完成，CPU 全程不参与像素运算。而 OpenCV `cvtColor` 跑在 CPU 上，640×480 BGR→NV12（约 900KB 数据）在 ARM Cortex-A55 上需要约 10~20ms，且会和推理后处理抢 CPU 时间片。

**② 与 DMA Buffer 天然兼容**

NV12 缓冲来自 `/dev/dma_heap/system`，具有 dmabuf fd。RGA 通过 `importbuffer_virtualaddr` 直接接管这块内存，MPP 编码器再通过 `mpp_buffer_import_with_tag` 把同一个 fd 导入——全程**一次内存分配，两个硬件模块共享**，没有任何 memcpy。

如果用 OpenCV，cv::Mat 的数据指针是普通 heap 内存，无法被 MPP 零拷贝访问，必须再做一次 CPU 拷贝才能喂给编码器，白白多了 450KB 的搬运开销。

**③ CPU 资源宝贵**

嵌入式场景下 CPU 需要同时跑三个线程 + 后处理 + 画框，RGA 相当于把色彩空间转换"外包"给专用硬件，让 CPU 专注控制流。

### 3.4ms 是怎么测出来的？

在 `yolov5s.cpp` 的 RGA 调用前后插 `std::chrono::steady_clock` 时间戳：

```cpp
auto t0 = std::chrono::steady_clock::now();
imcvtcolor(src_yuyv, dst_rgb, RK_FORMAT_YUYV_422, RK_FORMAT_RGB_888);  // RGA step A
auto t1 = std::chrono::steady_clock::now();
imresize(src_rgb, dst_model);                                             // RGA step B
auto t2 = std::chrono::steady_clock::now();

printf("RGA step A: %ld us, step B: %ld us\n",
    duration_cast<microseconds>(t1-t0).count(),
    duration_cast<microseconds>(t2-t1).count());
```

Step A（YUYV→RGB 640×480 色彩转换）约 1.8ms，Step B（RGB 640×480→640×640 缩放）约 1.6ms，合计约 **3.4ms**。这是 RGA 调用的同步等待时间，包含了 IOMMU 映射和硬件执行时间。

## 3. CPU 占用率有测过降低多少嘛？

做了 RGA 替代 OpenCV 前后对比测试（用 `top` 命令观察 `app` 进程的 CPU 占用）：

- **全部用 CPU/OpenCV 做色彩转换**（`cvtColor` YUYV→BGR、BGR→NV12）：CPU 占用约 **180%~220%**（多核合计，RK3588 有 4 大核 4 小核）
- **改用 RGA 做色彩转换**：CPU 占用降至约 **60%~90%**

降低幅度约 **120%~130%（绝对值）**，主要节省来自：
1. YUYV→RGB 两步 RGA 转换（原本是 RKNN 的 CPU 预处理）
2. BGR→NV12 RGA 转换（原本需要手写循环或 OpenCV）

画框（OpenCV `rectangle + putText`）仍在 CPU 上执行，这部分无法用 RGA 替代。

## 4. 端到端延迟怎么测试的？

采用**视觉对比法**：在摄像头前放一个手机显示秒表（精度 10ms），同时在 PC 端用 `ffplay` 拉 RTMP 流：

```bash
ffplay -fflags nobuffer -flags low_delay rtmp://192.168.137.1:1935/live/app
```

截屏同时记录：摄像头前实物秒表的数值 vs. ffplay 画面里秒表的数值，两者差值即为端到端延迟。

实测端到端延迟约 **200~400ms**，主要来自：

| 延迟来源 | 估计时间 |
|----------|----------|
| V4L2 帧采集 + DQ等待 | ~33ms（1帧，30fps） |
| RGA 预处理 × 2步 | ~3.4ms |
| NPU 推理（YOLOv5s 640×640） | ~20~30ms |
| 队列排队（SafeQueue 最深24帧） | 0~800ms（满载时） |
| RGA BGR→NV12 | ~2ms |
| MPP H.264 编码 | ~5~10ms |
| RTMP 网络传输（局域网） | ~10~50ms |
| ffplay 解码缓冲 | ~100ms |

代码中有 `t_start` 时间戳变量（`main.cpp:377`）但未被打印输出，属于"遗留调试代码"，实际延迟测量靠外部手工观测。

## 5. 整体 pipeline 讲一下，从摄像头采集到 RTMP 推流，数据流怎么流转的？

整体是**三线程流水线 + NPU 线程池**，数据以 **dmabuf fd（文件描述符）** 的形式在各硬件模块间传递，实现零拷贝。

```
摄像头（USB UVC，/dev/video0）
      │ V4L2_MEMORY_DMABUF，VIDIOC_DQBUF
      │ → FramePacket {dmabuf_fd, buffer_index}
      ▼
  [线程1：采集线程 captureThreadFunc]
      │ 压入 g_readQueue (SafeQueue<CapturedFrame>, cap=24)
      ▼
  [线程2：处理线程 processThreadFunc]
      │ submit_task_async(frame_index, dmabuf_fd)
      │       ↓ 线程池并行推理
      │  [NPU Worker 0] Yolov5s 实例 → RKNN_NPU_CORE_0
      │  [NPU Worker 1] Yolov5s 实例 → RKNN_NPU_CORE_1
      │       内部：
      │         RGA: YUYV→RGB888 (640×480, imcvtcolor)
      │         RGA: RGB888→RGB888 (640×480→640×640, imresize)
      │         RKNN: rknn_run() NPU推理
      │         CPU: NMS后处理，得到 detect_result_group_t
      │ std::future 按帧序 next_out 有序收集结果
      │ → YoloOutputFrame {dmabuf_fd, detections}
      │ 压入 g_writeQueue (SafeQueue<YoloOutputFrame>, cap=24)
      ▼
  [线程3：写出线程 writeThreadFunc]
      │ RGA: YUYV→BGR (importbuffer_fd + importbuffer_virtualaddr)
      │ OpenCV: rectangle+putText 画检测框（CPU）
      │ RGA: BGR→NV12 (importbuffer_virtualaddr × 2)
      │ MPP: mpp_buffer_import_with_tag(nv12_fd) 零拷贝编码 H.264
      │ FFmpeg: av_write_frame 写 RTMP + output.avi
      │ V4L2: VIDIOC_QBUF 归还摄像头缓冲
      ▼
   RTMP Server (rtmp://192.168.137.1:1935/live/app)
```

**关键零拷贝路径**：
- 摄像头→RGA→NPU：dmabuf fd 直传，RGA 和 NPU 通过 IOMMU 访问同一块 CMA 物理内存
- NPU 推理结果：只传递检测框坐标结构体（约几百字节），不传像素
- NV12→MPP：`dma_heap/system` fd 直接导入 MPP external buffer group，VPU 直接 DMA 读取

## 6. 摄像头帧率多少？分辨率多少？

- **分辨率：640 × 480**（`main.cpp:331-332`，硬编码）
- **格式：V4L2_PIX_FMT_YUYV**（YUYV422，每像素 2 字节，每帧 614,400 字节 ≈ 600KB）

```cpp
const int bitrate = 640 * 480 / 8 * 30;  // ≈ 1.1 Mbps，CBR 模式
```
GOP = 60（2秒一个 I 帧），H.264 High Profile Level 3.1。

## 7. 线程间同步用的什么机制？

项目使用了三层同步机制：

### ① SafeQueue —— 有界阻塞队列（线程间主要通信）

**文件：`SafeQueue.h`**

每个队列内部有：
```cpp
std::mutex m;                          // 保护 queue 和 stop_flag
std::condition_variable cond_not_empty; // 消费者等待有数据
std::condition_variable cond_not_full;  // 生产者等待有空位
size_t maxSize;                         // 队列容量上限（24）
```

`enqueue()`：加锁 → 等待 `cond_not_full`（队列已满时阻塞）→ push → 通知 `cond_not_empty`

`dequeue()`：加锁 → 等待 `cond_not_empty`（队列空时阻塞）→ pop → 通知 `cond_not_full`

这是标准的**生产者-消费者**模式，满队时上游自动反压阻塞，空队时下游自动阻塞等待。

### ② std::future / std::packaged_task —— NPU 异步任务结果同步

**文件：`pool/thread_poll.cpp`**

```cpp
// 提交任务，立即返回 future
std::future<ProcessResult> fut = npu_pool.submit_task_async(index, dmabuf_fd);

// 处理线程轮询，1ms 超时，不阻塞整个线程
auto status = fut.wait_for(std::chrono::milliseconds(1));
if (status == std::future_status::ready) { /* 取结果 */ }
```

线程池内部用 `std::mutex queue_mutex + std::condition_variable` 保护任务队列。Worker 线程 `wait` 在 condition variable 上，有任务时被 `notify_one` 唤醒。

### ③ std::atomic<bool> —— 轻量级状态标志

**文件：`main.cpp:98-99`**

```cpp
std::atomic<bool> g_readFinish{false};    // 采集线程置位，通知处理线程
std::atomic<bool> g_processFinish{false}; // 处理线程置位，通知写出线程
```

无需加锁，原子读写保证跨线程可见性，用于流水线优雅退出。

### ④ MAX_INFLIGHT 限制 —— 反压控制

处理线程维护一个 `inflight` map，最多允许 8 个 NPU 任务同时在途（`main.cpp:184`），超过后停止提交新任务，让采集队列自然积压，进而阻塞采集线程——形成全链路反压。

## 8. 有没有遇到过生产者消费者速率不匹配的问题，怎么解决的？

遇到过，主要有两种场景：

### 场景一：NPU 推理速度 < 摄像头帧率

摄像头 30fps 持续产帧，每帧推理约 20~30ms（= ~33fps 上限），在双核 NPU 并行时推理吞吐约 60fps，理论上不是瓶颈。但实际由于 `MAX_INFLIGHT=8` 的限制，当写出线程慢时，inflight 任务积压到上限，采集线程被 SafeQueue 反压阻塞，摄像头实际采集速率自动降低，而不是丢帧。

**解决方案：有界阻塞队列 + inflight 上限双重反压**

### 场景二：写出线程（画框+编码+推流）慢于推理

写出线程需要串行执行 RGA + OpenCV + MPP + RTMP，偶发 RTMP 网络抖动时会进一步拖慢。这时 `g_writeQueue` 逐渐积满（最多 24 帧），处理线程的 `enqueue` 阻塞，进一步让 inflight 任务无法下发，最终阻塞采集线程。

**解决方案**：
1. **有界队列自然反压**：不丢帧，用背压控制整体节奏
2. **V4L2 buffer 自然反压**：写出线程持有 dmabuf fd 直到 `releaseFrame`（QBUF），若写出慢，V4L2 的 4 个 buffer 全部在外流转，`captureFrame` 的 `poll()` 会一直等不到 DQBUF，采集线程自然等待
3. **CMA 内存压力**：将 V4L2 缓冲从 6 个减到 4 个（节省 1.2MB CMA），减少同时在途的帧数，降低内存压力，也间接限制了最大队列深度

**注意**：项目没有帧丢弃机制。所有速率不匹配都通过阻塞反压解决，保证每帧都被处理和推流，代价是端到端延迟会随队列积压增加。

## 9. 各模块之间用什么方式传递数据（共享内存？队列？）

### 线程间：SafeQueue 传递轻量元数据 + dmabuf fd

```cpp
// 队列元素只传 fd 和检测结果，不传像素数据
struct CapturedFrame {
    int index;
    FramePacket_t packet;   // 含 dmabuf_fd（一个整数）
};

struct YoloOutputFrame {
    int index;
    FramePacket_t packet;
    detect_result_group_t detections;  // 检测框，~2KB 结构体，值拷贝
};
```

像素数据（600KB/帧的 YUYV）始终留在 CMA 物理内存里，各线程通过 `dmabuf_fd` 这个"指针"访问，**不做内存拷贝**。

### NPU 任务：std::future 异步传递推理结果

处理线程 submit 任务后得到 `future<ProcessResult>`，NPU worker 完成推理后通过 `packaged_task` 写入结果，处理线程 poll `wait_for(1ms)` 取结果，再包装到 `YoloOutputFrame` 压入写队列。

### 硬件模块间：dmabuf fd（零拷贝共享内存）

```
V4L2 CMA buffer ──(fd)──▶ RGA(importbuffer_fd) ──▶ rknn_create_mem buffer ──(fd)──▶ NPU
                                                                                    ↓
nv12 dma_heap/system buffer ──(fd)──▶ RGA(importbuffer_virtualaddr) ──(fd)──▶ MPP
```

本质是**共享内存（DMA Buffer）**，但不是传统 POSIX shm，而是通过 Linux DMA-BUF 框架，由内核保证跨驱动的物理内存共享和 cache 一致性（`DMA_BUF_SYNC_START/END` ioctl）。

### 总结

| 传递内容 | 方式 | 是否拷贝 |
|----------|------|----------|
| 帧元数据（fd、序号） | SafeQueue 值传递 | 拷贝（但只有几十字节） |
| 像素数据（YUYV） | dmabuf fd 共享 | **不拷贝** |
| NPU 推理结果（检测框） | std::future 值传递 | 拷贝（~2KB） |
| NPU 输入/输出张量 | rknn_create_mem fd 绑定 | **不拷贝** |
| NV12 编码输入 | dma_heap fd 导入 MPP | **不拷贝** |

## 10. 多线程流水线怎么设计的？采集、推理、编码、推流各几个线程？

### 线程设计

| 阶段 | 线程名 | 线程数 | 文件位置 |
|------|--------|--------|----------|
| 采集 | `captureThreadFunc` | **1个** | `main.cpp` |
| 推理 | `processThreadFunc` + NPU worker | **1 + 2个** | `main.cpp` + `pool/thread_poll.cpp` |
| 编码+推流 | `writeThreadFunc` | **1个** | `main.cpp` |

总计：**5个工作线程**（1采集 + 1调度 + 2 NPU worker + 1写出），加上 main 线程共 6 个。

### 为什么这样设计？

**采集用 1 个线程**：V4L2 `poll + DQBUF` 是同步 IO，单线程按序出队足够，超过 1 个无意义（只有一路摄像头）。

**推理用 1调度 + N worker 的线程池**：
- 调度线程（`processThreadFunc`）负责维护帧序号（`next_out`）和 inflight 任务数（≤8），保证有序输出
- NPU worker 线程并行执行 RKNN 推理，绑定不同 NPU core，实现三核并行（实际因 CMA 压力用 2 个）
- 用 `std::future` 解耦提交和收取，调度线程非阻塞轮询，不浪费 CPU

**编码+推流用 1 个线程**：MPP 编码器和 FFmpeg RTMP 均为顺序处理，且需要严格帧序，单线程串行最简单正确。画框（OpenCV）也在这里，CPU 消耗可接受。

### 流水线并行效果

```
时间轴 →

帧 N  : [采集] ──────▶ [推理] ──────────────▶ [编码推流]
帧 N+1:           [采集] ──────▶ [推理] ──────────────────▶ [编码推流]
帧 N+2:                    [采集] ──────▶ [推理] ──────────────────────▶ [编码推流]
```

三个阶段并行执行，理想情况下吞吐量由最慢的阶段决定（目前瓶颈是写出线程，约 33fps）。

## 11. 三核 NPU 并行怎么实现的？

RK3588 的 NPU 包含 3 个独立算力核心，总算力 6 TOPS（每核 2 TOPS）。RKNN SDK 提供 `rknn_set_core_mask` API 指定推理使用哪个核。

### 实现方式：每个线程独占一个 NPU core + 一个 RKNN context

**文件：`yolov5s.cpp:60-77`，`pool/thread_poll.cpp:53`**

```cpp
// yolov5s.cpp 构造函数
rknn_init(&context, model_data, model_size, RKNN_FLAG_PRIOR_HIGH, nullptr);

// 根据线程编号绑定核心
rknn_core_mask core_mask;
switch (npu_index % 3) {
    case 0: core_mask = RKNN_NPU_CORE_0; break;
    case 1: core_mask = RKNN_NPU_CORE_1; break;
    default: core_mask = RKNN_NPU_CORE_2; break;
}
rknn_set_core_mask(context, core_mask);
```

```cpp
// thread_poll.cpp：创建线程池时，每个 worker 创建独立 Yolov5s 实例
for (int i = 0; i < PROCESS_THREAD_NUM; i++) {
    yolo_instances.emplace_back(model_path, i);  // i 即 npu_index
    workers.emplace_back(&ThreadPoll::worker, this, i);
}
```

**关键点**：
- 每个 RKNN context 是独立的，有自己的权重副本和 IO buffer，互不干扰
- `rknn_run()` 调用是同步阻塞的，但因为绑定了不同 core，三个 context 可以真正并行执行
- IO buffer（`input_mem_`、`output_mems_`）通过 `rknn_create_mem + rknn_set_io_mem` 预分配并绑定，避免每帧重新分配

### 为什么实际只用了 2 核？

CMA 内存限制（RK3588 CmaTotal = 8MB）：
- V4L2 采集缓冲：4 × 600KB ≈ 2.4MB
- 每个 RKNN 实例内部占用约 3~4MB（权重 + 中间缓冲）

3 个实例同时初始化时 CMA 不足，`rknn_init` 或 `rknn_create_mem` 报 OOM。解决方案：减少到 2 个实例（2 核），CMA 占用降至可接受范围。若在内核启动参数里加 `cma=32M` 可恢复 3 核并行。

## 12. V4L2 采集用的 MMAP 还是 USERPTR？buffer 数量设了几个？

### 内存模式：**V4L2_MEMORY_DMABUF**（既不是 MMAP 也不是 USERPTR）

**文件：`camera/v4l2_camera.cpp:68`**

```cpp
req.memory = V4L2_MEMORY_DMABUF;
```

**三种模式对比**：

| 模式 | 内存分配者 | 数据访问方式 | 是否零拷贝 |
|------|-----------|-------------|-----------|
| MMAP | 内核驱动 | 用户 mmap 后直接访问 | 半（仍需 CPU 读） |
| USERPTR | 用户态 | 用户分配，传指针给驱动 | 否（需要物理连续） |
| **DMABUF** | **用户态（dma_heap）** | **fd 引用，IOMMU 访问** | **是** |

选 `V4L2_MEMORY_DMABUF` 的原因：摄像头驱动通过 DMA 直接写入 CMA 物理连续内存，用户态拿到 `dmabuf_fd` 后，直接传给 RGA 和 RKNN 的 `importbuffer_fd()`，整个从摄像头到 NPU 的路径上**没有任何 CPU 参与的数据搬运**。

### Buffer 数量：**代码中配置 6 个，实际运行用 4 个**

**文件：`main.cpp:47`**

```cpp
constexpr int BUFFER_NUM = 6;  // 代码中的常量
```

但 `conclude/链路.md` 记录：由于 CMA 内存压力（6 个 buffer × 600KB = 3.6MB，加上 RKNN 的 3~4MB，超出 8MB CmaTotal），实际运行时将 `BUFFER_NUM` 改为 **4**，总占用约 2.4MB，CMA 才够用。

### Buffer 生命周期

```
初始化：queueAllBuffers() → 4个 buffer 全部 VIDIOC_QBUF 给驱动
采集：  captureFrame() → poll() 等待就绪 → VIDIOC_DQBUF 取出一帧
             → DMA_BUF_SYNC_START (cache invalidate，保证 CPU 读到新数据)
使用中：frame 在流水线中以 fd 形式传递，buffer 一直在用户态持有
归还：  writeThreadFunc 末尾 releaseFrame()
             → DMA_BUF_SYNC_END
             → VIDIOC_QBUF 还给驱动，供下一帧使用
```

设备以 `O_NONBLOCK` 打开，`captureFrame` 内部用 `poll()` 阻塞等待帧就绪，避免忙等。

## 2. 内存对齐具体对齐到多少字节，为什么是这个值？

### 项目中使用了两种对齐粒度

**① 16字节对齐 —— 用于图像宽高步长（hor_stride / ver_stride）**

定义位置：`main.cpp:36` 和 `mpp/mpp.h:21`
```cpp
#define ALIGN(x, a)     (((x) + (a)-1) & ~((a)-1))   // main.cpp
#define MPP_ALIGN(x, a) (((x)+(a)-1)&~((a)-1))        // mpp/mpp.h
```

使用方式：
```cpp
// main.cpp:338-339
g_hor_stride = ALIGN(width, 16);    // 640 → 640（已对齐）
g_ver_stride = ALIGN(height, 16);   // 480 → 480（已对齐）

// mpp/mpp.c:186-187
mpp_enc_data->hor_stride = MPP_ALIGN(width, 16);
mpp_enc_data->ver_stride = MPP_ALIGN(height, 16);
```

**为什么是 16 字节？**

RGA 硬件和 MPP（VPU）编码器对 NV12/YUV 格式有最低 16 字节宽度对齐要求，原因是：
- RGA 的 DMA burst 读取单位是 16 字节（128-bit 总线宽度）
- H.264 的宏块（Macroblock）大小是 16×16 像素，编码器内部以 16 为粒度处理亮度块
- 步长不对齐会导致 RGA 报 "wstride < width" 错误，MPP 出现花屏

本项目分辨率 640×480，两个维度均已经是 16 的倍数，所以步长等于分辨率，无需填充。但如果用 720×480，水平步长需填充为 `ALIGN(720, 16) = 720`（恰好也是 16 的倍数）；若误用 64 字节对齐则步长变成 768，会出现 48 列不可见 padding 行（`conclude/总结.md` 中记录的一个 bug）。

**② 64字节对齐 —— 用于计算 MPP 内部 frame_size**

```cpp
// mpp/mpp.c:192
frame_size = MPP_ALIGN(hor_stride, 64) * MPP_ALIGN(ver_stride, 64) * 3 / 2;
// = ALIGN(640, 64) * ALIGN(480, 64) * 3 / 2
// = 640 * 512 * 3 / 2 = 491,520 字节（仅用于 MPP 内部 buffer 大小分配）
```

**为什么是 64 字节？**

这是 RK3588 VPU 的 DMA 突发传输对齐要求和 CPU cache line 对齐（ARM 标准 cache line = 64 字节）。仅影响内部分配缓冲大小，不影响实际图像数据布局（图像数据仍按 16 字节步长存储）。

## 3. CMA内存池大小怎么确定的？

### RK3588 CMA 总量限制

RK3588 内核默认 `CMA Total = 8MB`（通过 `cat /proc/meminfo | grep Cma` 确认）。整个系统所有需要物理连续内存的驱动（摄像头、NPU、VPU 等）共用这 8MB。

### 各模块 CMA 消耗分析

| 模块 | buffer来源 | 单块大小 | 数量 | 合计 |
|------|-----------|---------|------|------|
| V4L2 摄像头采集缓冲 | `/dev/dma_heap/cma` | 640×480×2 = 600KB | **4个** | **2.4MB** |
| RKNN 每实例 mid_mem（中间RGB缓冲） | `rknn_create_mem`（内部DMA heap） | 640×480×3 = 900KB | 2个实例 | 1.8MB |
| RKNN 每实例 input_mem（模型输入） | `rknn_create_mem` | 640×640×3 ≈ 1.2MB | 2个实例 | 2.4MB |
| RKNN output_mems（3层特征图） | `rknn_create_mem` | ~1MB合计 | 2个实例 | ~2MB |
| NV12 写出工作缓冲 | `/dev/dma_heap/system`（**非CMA**） | 640×480×1.5 = 450KB | 1个 | 不占CMA |
| MPP 编码器 pkt_buf | MPP内部DMA heap | ~1MB | 1个 | ~1MB |

**CMA 实际消耗约 4.2MB**（V4L2 的 2.4MB + RKNN 约 1.8MB），留有约 3.8MB 余量。

### 确定过程 —— 踩坑法

**初始配置（6个V4L2 buffer + 3个NPU实例）**：
- V4L2：6 × 600KB = 3.6MB
- RKNN × 3 实例：~4MB
- 合计约 7.6MB，超过 8MB → `rknn_create_mem` 返回 OOM，系统报 `dma_heap_alloc: failed`

**调整方案**：
1. 将 V4L2 buffer 从 6 个减到 **4 个**，节省 1.2MB CMA → V4L2 降至 2.4MB
2. 将 NPU 实例从 3 个减到 **2 个**，节省约 2MB CMA → RKNN 降至约 2MB
3. NV12 缓冲改用 `/dev/dma_heap/system`（非物理连续，IOMMU访问，**不消耗CMA**）→ 节省 450KB

**最终消耗约 4.2MB，低于 8MB 阈值，系统稳定运行。**

若需恢复 3 个 NPU 实例（3核并行），需在内核启动参数中增加 `cma=32M`。

## 4. DMA-BUF的fd是从哪里申请的，RKISP、RGA、NPU、MPP之间怎么传递？

### fd 申请来源

本项目使用 USB 摄像头（UVC驱动），非 RKISP，但 fd 申请机制相同。

| fd | 申请位置 | 申请方式 |
|----|---------|---------|
| V4L2 采集缓冲 fd | `camera/cma_buffer.cpp` | `ioctl(cma_heap_fd, DMA_HEAP_IOCTL_ALLOC, &alloc)` → `alloc.fd` |
| RKNN mid_mem fd | `yolo/yolov5s.cpp` | `rknn_create_mem(context, size)` → `mem->fd` |
| RKNN input_mem fd | `yolo/yolov5s.cpp` | `rknn_create_mem(context, size)` → `mem->fd` |
| NV12 写出缓冲 fd | `main.cpp` | `ioctl(system_heap_fd, DMA_HEAP_IOCTL_ALLOC, &alloc)` → `alloc.fd` |

```cpp
// camera/cma_buffer.cpp: 从 /dev/dma_heap/cma 申请物理连续内存
struct dma_heap_allocation_data alloc = {
    .len   = size,
    .fd_flags = O_CLOEXEC | O_RDWR,

ioctl(heap_fd, DMA_HEAP_IOCTL_ALLOC, &alloc);
fd_ = alloc.fd;  // 这就是 dmabuf fd
```

```
┌─────────────────────────────────────────────────────────────────────┐
│  /dev/dma_heap/cma                                                  │
│  ioctl(DMA_HEAP_IOCTL_ALLOC) → v4l2_fd[0..3]（YUYV 600KB×4）      │
└───────────────────────┬─────────────────────────────────────────────┘

                        ▼

│  importbuffer_fd(v4l2_fd, ...)         → h_yuyv                    │
│  importbuffer_virtualaddr(bgr_buf, ...) → h_bgr                    │

│                                                                      │

│  mpp_buffer_import_with_tag(ext_grp, &info, &frm_buf, ...)         │
│  mpp_frame_set_buffer(frame, frm_buf)                               │
│  encode_put_frame(ctx, frame)   [VPU通过DMA直接读NV12，零拷贝]     │
│  encode_get_packet → av_write_frame → RTMP推流                      │
└─────────────────────────────────────────────────────────────────────┘
```

### 关键技术细节

**RGA 使用 Linux API（非 Android API）**：
- 正确方式：`importbuffer_fd()` → `rga_buffer_handle_t` → `wrapbuffer_handle()`
- 错误方式（踩过坑）：Android 专用的 `wrapbuffer_fd()` 宏参数顺序不同，导致 "wstride < width" 错误

**MPP 导入类型必须用 EXT_DMA**（`mpp/mpp.c`）：
- 正确：`MPP_BUFFER_TYPE_EXT_DMA` + `mpp_buffer_group_get_external`
- 错误（踩过坑）：`MPP_BUFFER_TYPE_DMA_HEAP` + 内部 group → 报 `MPP_ERR_NOMEM (-2)`

**cache 同步**：V4L2 在 DQBUF 前调用 `DMA_BUF_SYNC_START`（invalidate CPU cache），确保 CPU 能读到 DMA 写入的最新数据；在 QBUF 前调用 `DMA_BUF_SYNC_END`（flush cache），确保 DMA 读到 CPU 写入的数据。

## 7. 队列满了怎么处理，丢帧还是阻塞？

### 结论：**阻塞（Backpressure）, 不丢帧**

### SafeQueue 实现细节（`SafeQueue.h:18-28`）

```cpp
void enqueue(const T &t) {
    unique_lock<mutex> lock(m);
    // 队列满时挂起等待，直到有空位或收到 stop 信号
    cond_not_full.wait(lock, [this]{
        return stop_flag || q.size() < maxSize;
    });
    if (stop_flag) { return; }
    q.push(t);
    cond_not_empty.notify_one();
}

bool dequeue(T &t) {
    unique_lock<mutex> lock(m);
    // 队列空时挂起等待，直到有数据或收到 stop 信号
    cond_not_empty.wait(lock, [this]{
        return stop_flag || !q.empty();
    });
    if (stop_flag && q.empty()) { return false; }
    t = q.front(); q.pop();
    cond_not_full.notify_one();
    return true;
}
```

### 两条队列的容量

| 队列 | 变量名 | 容量 | 生产者 | 消费者 |
|------|-------|------|--------|--------|
| 采集→推理 | `g_readQueue` | `READ_QUEUE_CAP = 24` | 采集线程 | 处理线程 |
| 推理→写出 | `g_writeQueue` | `WRITE_QUEUE_CAP = 24` | 处理线程 | 写出线程 |

### 三层反压机制

**第一层：SafeQueue 有界阻塞**
- `g_writeQueue` 满（24帧积压）→ 处理线程的 `enqueue` 阻塞
- `g_readQueue` 满（24帧积压）→ 采集线程的 `enqueue` 阻塞

**第二层：MAX_INFLIGHT 限制（`main.cpp:184`）**
```cpp
constexpr size_t MAX_INFLIGHT = 8;
// 处理线程：当 NPU 在途任务数 >= 8 时，停止从 g_readQueue 取帧
while (inflight.size() >= MAX_INFLIGHT) {
    // 轮询已完成的 future，不提交新任务
}
```
这使 `g_readQueue` 提前积压，比等到写队列满更早施压给采集线程。

**第三层：V4L2 缓冲区自然反压**
- 写出线程在编码完成后才调用 `releaseFrame()`（VIDIOC_QBUF 归还缓冲）
- 若写出线程慢，4个 V4L2 buffer 全部在流水线中占用
- 采集线程 `poll()` 等不到就绪缓冲，自然阻塞

### 代价

不丢帧的代价是**延迟增加**：24帧队列在 30fps 下可积压 800ms 延迟。若业务对实时性要求更高（如自动驾驶），应改为固定延迟的**丢帧策略**（队列满时丢弃最旧帧或最新帧），当前项目为监控场景，优先保证录制完整性，选择阻塞反压。

## 8. 三个阶段（采集、推理、推流）各用了几个线程？

### 线程总览

| 阶段 | 线程函数 | 线程数 | 作用 |
|------|---------|--------|------|
| **采集** | `captureThreadFunc` | **1个** | V4L2 poll+DQBUF，DMA_BUF_SYNC，压入 g_readQueue |
| **推理（调度）** | `processThreadFunc` | **1个** | 从 g_readQueue 取帧，向线程池提交任务，有序收集结果，压入 g_writeQueue |
| **推理（执行）** | NPU worker × 2 | **2个** | 各持一个 Yolov5s 实例，绑定 RKNN_NPU_CORE_0/1，执行 RGA预处理+NPU推理+后处理 |
| **推流** | `writeThreadFunc` | **1个** | RGA色彩转换，OpenCV画框，MPP H.264编码，FFmpeg RTMP推流，VIDIOC_QBUF还帧 |
| **主线程** | `main` | 1个 | 初始化所有模块，启动线程，join等待 |

**工作线程合计：5个（1采集 + 1推理调度 + 2 NPU worker + 1推流）**
**总线程数：6个（含主线程）**

### 为什么这样分配？

**采集 1 个线程**：
V4L2 是顺序帧源，单线程 `poll() + DQBUF` 足够，多线程无法加速单路摄像头。

**推理 1调度 + 2worker 的设计**：
- 调度线程负责维护 `next_out` 帧序号计数器，保证输出到写队列的帧严格有序（NPU 并行时可能帧 N+1 先完成，必须等帧 N 完成后才能一起输出）
- Worker 线程各自绑定一个 NPU core，实现真正的硬件并行推理（`rknn_set_core_mask`）
- 用 `std::future + packaged_task` 解耦提交和收取，调度线程以 1ms 超时轮询，不阻塞
- 原计划 3个 worker（3核并行），因 CMA 内存不足降为 2个

**推流 1 个线程**：
MPP 编码器要求帧严格顺序输入（CBR 码率控制依赖帧序），FFmpeg RTMP 也是顺序写出，单线程串行最简单且正确。

### 推理阶段的帧序保证机制

```
                   [worker 0] frame 0 → future_0 (完成时间: t+25ms)
processThread →                                                    → 按 next_out 有序输出
                   [worker 1] frame 1 → future_1 (完成时间: t+22ms)

processThread 维护 next_out=0，先 poll future_0：
  - future_1 先完成 → 但 next_out 还是0，暂存 pending_results[1]
  - future_0 完成   → 输出 frame_0，next_out=1
  - 发现 pending_results[1] 已就绪 → 立即输出 frame_1，next_out=2
```

这保证了无论 NPU 两个 core 谁先完成，写出线程收到的帧序始终为 0,1,2,3,...，编码出的视频不会出现帧序混乱。
